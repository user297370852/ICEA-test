# ICAE-Bench 论文通俗解读（写给软件工程师）

> 论文：**ICAE-Bench: Evaluating Coding Agents as Interactive Project Builders**
> （交互式编码智能体评测基准：把编码智能体当作"项目搭建者"来考察）
>
> 作者来自复旦大学、美团、新加坡管理大学等。官方代码仓库：<https://github.com/ALEX-nlp/ICAE-EVAL>（已克隆到本文档同级的 `ICAE-EVAL/` 目录）。

---

## 一句话总结

这篇论文造了一个"考试"（benchmark），专门考察 AI 编码智能体（比如 Claude Code、OpenHands 这类工具）在**需求模糊**的情况下，能不能像一个靠谱的开发者那样：**先问清楚需求，再从零搭建出一个能跑的完整项目**。结论是：目前最强的模型也只能通过 38.2% 的测试——AI 会"抄可见的例子"，但对隐藏约束、边界情况和长周期的工程整合仍然很吃力。

---

## 1. 背景：为什么需要这个benchmark

### 1.1 什么是 "Vibe Coding"

传统编程是：需求文档写得很清楚 → 开发者照着实现。而最近流行的 "vibe coding"（氛围编程）是：用户只说一句模糊的话，比如"帮我做个解析配置文件、报告非法项的小工具"，就把整个项目丢给 AI 去做。这时 AI 必须：

1. 意识到需求里**缺了什么**（文件格式是什么？重复的 key 算不算错？错误怎么报告？）
2. **主动提问**澄清这些缺口
3. 规划项目结构、选实现方案
4. 写代码、装依赖、自己跑测试、自己修 bug
5. 交付一个**可运行**的完整项目

这已经不只是"写代码"了，而是把软件工程的很大一部分（需求澄清、设计、构建、验证）都交给了 AI。

### 1.2 现有的"考试"考察不了这件事

已有的编码评测基准分几类，但都和真实 vibe coding 场景脱节：

| 基准类型 | 例子 | 问题 |
|---|---|---|
| 函数级 | HumanEval、MBPP | 只考"补一个函数"，需求是完整给定的 |
| 仓库内修 bug | SWE-bench 系列 | 仓库已存在，只考打补丁 |
| 从零生成项目 | Commit0、NL2RepoBench、PRDBench | 更接近了，但需求文档写得太详细，或者把接口签名、项目骨架都给了 |

也就是说，**没有哪个基准同时满足**：需求一开始是模糊的 + 智能体可以通过提问澄清 + 最后从零交付一个完整、可测试的仓库。ICAE-Bench 就是补这个空缺的。

## 2. ICAE-Bench 是怎么设计的

### 2.1 核心思想："从精确中派生模糊"

设计一个"模糊需求"的考试有个两难：

- 需求写得太模糊 → 根本没法判卷（正确答案不唯一，AI 没做对可能是因为题目本身有毛病，而不是 AI 不行）
- 需求写得太清楚 → 又回到了老路，考不出"澄清需求"的能力

ICAE-Bench 的解法非常巧妙，分三步：

1. **先找一个真实存在的开源仓库**，要求它自带的测试能在 Docker 里全部跑通（保证有一个"标准答案"，行为精确可验证）；
2. **从仓库反推一份详尽的需求文档**（GroundPRD），并把原仓库的测试改造成标准化的"黑盒测试用例"（JSON 格式的输入 → 期望输出，不依赖原仓库的代码结构）；
3. **再把 GroundPRD "做模糊化"（fuzzify）**——故意藏起一部分约束（API 细节、边界情况、架构要求），变成一份简短的"产品经理式的模糊需求"（Fuzzy PRD，平均只有 276 个 token，而 GroundPRD 平均 6764 个 token）。

被测的 AI 看到的是模糊需求，但判卷用的是那份精确的黑盒测试。**"需求暴露"和"行为评判"被解耦了**。

### 2.2 关键机制一：User Agent（模拟用户的智能体）

被测 AI 可以提问，那谁来回答？如果用真人或让大模型自由发挥，会出现不可复现、瞎编需求、泄露答案等问题。ICAE-Bench 的做法：

- 把所有被藏起来的约束，在"模糊化"阶段就整理成一份**结构化的 User Agent Data**（JSON）：每条包含约束编号、触发关键词、标准回答、上下文指引，外加一个兜底回复（fallback）。
- 用一个 LLM（默认 DeepSeek-V3.2）扮演"严格的 Tech Lead"，做**路由器**：你问到点上（命中触发关键词）→ 返回预先写好的答案；问得不对 → 原样返回兜底回复，绝不自由发挥。
- 每次提问有**预算限制**（默认 16 个问题），每次回答最多覆盖 3 个约束点。

这样，"向用户提问"就变成了一条**可测量、可复现的评测通道**：能统计出 AI 问对了多少约束（覆盖率）、多少问题打了空枪（fallback 率）、预算用了多少。

> 用软件工程的话说：相当于把"需求澄清会议"的会议纪要提前写好了，用户角色只能照着纪要回答，不能即兴发挥。

### 2.3 关键机制二：模糊度的三个等级

同一个任务（同一套黑盒测试）配四个档次的初始需求，信息量递增：

- **Fuzzy L1**：最模糊，一段简短的产品需求，藏起大量约束
- **Fuzzy L2**：恢复 L1 中被藏的一部分约束
- **Fuzzy L3（Easy）**：保留 GroundPRD 大部分内容，只删少量细节
- **GroundPRD**：完整需求文档（作为"上限"参照）
- 另有一个 **RecoveredPRD**：把 L1 场景下所有问答记录直接拼在模糊需求后面（考"信息都给你了但不整理"的效果）

这样就能做**控制变量实验**：同一个任务，初始信息量不同，看成绩差多少，从而区分"是信息不够"还是"能力不行"。

### 2.4 关键机制三：黑盒测试 + 语言无关评测

- 原仓库的测试被重构成标准化的 JSON 黑盒用例（**Native** 用例）；另外针对边界值、压力场景等**合成增强用例（Enhanced）**。
- 按可见性分：**Public** 用例（写在 GroundPRD 里的示例，L1/L2 下要靠提问才能拿回）和 **Hidden** 用例（判卷用）。
- 黑盒用例只看"输入什么、输出什么"，**不管你用什么语言、什么架构实现**——所以论文里甚至做了"把所有非 Python 任务都用 Python 重写"的跨语言实验。

### 2.5 关键机制四：Ultimate Image（终极镜像）

每个任务打包成一个 Docker 镜像：先在官方语言基础镜像（如 `python:3.11`、`golang:1.22` 等 12 种）里把原仓库跑通、装好依赖，然后**删掉原代码、原测试和一切"答案痕迹"**，只留下一个配好环境的空壳。被测 AI 在这个容器里从零开发。判卷时再开一个全新容器，注入权威测试用例来跑 AI 交付的代码。

### 2.6 数据规模

- 完整版 **480 个任务**，覆盖 **12 种语言**（C#、C++、Dart、Go、Java、JavaScript、Kotlin、PHP、Python、Ruby、Rust、TypeScript），每种 40 个
- **ICAE-Bench-Lite**：按代码量挑出最小的 50 个任务，用于快速做消融实验

### 2.7 评测指标（四组）

| 指标组 | 内容 | 通俗理解 |
|---|---|---|
| 功能正确性 | Public / Native / Enhanced / Overall 通过率 | "代码跑得对不对" |
| 智能体评估（Critic 打分） | 语义相似度、API 相似度、设计质量 | 让一个评审 LLM 对比 AI 的产出和原仓库，打三个 0–100 分 |
| 结构评估 | 文件数/代码行比例、类/方法相似度 | "做出来的项目规模和结构像不像原项目"（诊断是偷工减料还是过度工程） |
| 交互质量 | 约束覆盖率、fallback 率、预算使用率 | "问题问得好不好" |

## 3. 实验结果：说了什么

被测模型：GPT-5.5、Claude-Opus-4.8、Claude-Sonnet-4.6、GLM-5.1、Gemini-3.1-Pro、MiniMax-M2.5，跑在 Claude Code 和 OpenHands 两个智能体框架下。

### 主要数字

- 全量基准上最好的 Overall 通过率只有 **38.2%**（Claude-Opus-4.8），第二名 GPT-5.5 是 37.2%，最弱的 MiniMax-M2.5 只有 0.8%。
- **Public 通过率普遍高于 Enhanced**：说明 AI 擅长"复现看得见的例子"，但看不见的边界、鲁棒性场景就露馅——有点像"过拟合样例"。
- 一个仓库全部用例都通过的（Clean）非常少：480 个里每个模型只有 1–13 个。
- **功能分数相近的模型，工程风格天差地别**：Claude-Opus-4.8 生成的文件数是原仓库的 337%、代码行数 981%（疯狂膨胀）；GLM-5.1 只有 12%/16%（严重缩水）。分数差不多，做法完全不同。
- **问得多 ≠ 做得好**：GPT-5.5 的约束覆盖率（73.7%）比 Claude-Opus-4.8（69.6%）高，Overall 反而低 1 分。

### 最有意思的发现："信息→执行"鸿沟

按直觉，给 AI 的需求信息越多，成绩应该越好。实验发现只对了一半：

- **GroundPRD（完整需求）对 6 个模型中的 4 个仍是最好的**，即使把 L1 下所有能问到的问答记录原封不动拼给 AI（RecoveredPRD），成绩仍然不如一份组织良好的完整文档。
- **把 Public 测试用例直接以可执行文件的形式放进工作区**（而不是靠提问获得零散信息），GLM-5.1 的 Overall 从 37.4% 暴涨到 **61.8%**——尽管约束覆盖率反而略降。

结论：**瓶颈不在于"拿到信息"，而在于"把信息组织好、记住、并转化为可执行、可验证的实现"**。可直接运行、可调试的反馈比更多的需求信息更有用。这就是论文说的两个 gap：

1. **需求获取 gap**：模糊需求 ↔ 能通过提问拿回的信息（提问能弥补一部分）
2. **信息到执行 gap**：拿到的信息 ↔ 正确的仓库（提问弥补不了，靠的是信息组织、保持和验证能力）

### 其他消融结论（RQ4）

- **智能体框架很重要**：同样的模型从 Claude Code 换到 OpenHands，Overall 全员下降 5.5–21.8 分，GPT-5.5 掉得最狠（-21.8），排名都变了。框架的编辑、执行、状态跟踪能力直接决定成绩。
- **提问预算不是越多越好**：预算 8/16/24 对应 Overall 22.9%/37.4%/34.4%。16 个问题名义上已经够问回 20 来个约束点，加到 24 反而引入更多冗余信息，增加整合负担。
- **User Agent 换模型**：换更强/更弱的路由模型，检索到的约束更多 ≠ 成绩更好。
- **开思考（thinking）模式有稳定收益**：Gemini-3.1-Pro 开思考从 26.7% → 36.6%；GLM-5.1 自适应思考比固定 8k 思考高 2.6 分。
- **环境越富不一定越好**：用预装好依赖的 ultimate 镜像（而不是干净的基础镜像），Overall 反而从 37.4% 掉到 28.4%，且生成代码膨胀到原仓库的 191% 文件数 / 674% 代码行——选择太多导致过度设计。
- **跨语言实现可行**：把非 Python 任务全部改用 Python 实现，Overall 从 26.6% → 29.9%，验证了黑盒评测的语言无关性。

### 失败模式分类（像崩溃日志分析一样给失败归因）

- **Mismatch**：跑出来了但输出不对（逻辑错误）
- **Missing**：部分用例没输出（功能覆盖不全）
- **Exec**：构建/运行就崩了（依赖、环境问题）
- **No Test**：没按规范交出 `rcb_tests/test.sh` 入口（没读懂题/不守规矩）

强模型多为 Mismatch（能跑但行为不对），弱模型多为 No Test / Exec。

## 4. 论文的贡献与局限（我的点评）

**贡献：**
1. 第一个把"需求澄清交互"和"从零仓库生成"结合起来的大规模基准（480 任务 × 12 语言）；
2. "从精确派生模糊"的构造方法 + 受控的 User Agent，让"模糊性"变得可评测、可复现——这是方法论上最漂亮的部分；
3. 多维指标（功能/结构/语义/交互）能定位失败发生在链条的哪一环。

**局限（论文自己也承认了一部分）：**
- Lite 子集与全量排名只有中等一致（Spearman ρ=0.71），Lite 上 GPT-5.5 第一、全量上 Claude-Opus-4.8 第一，用 Lite 做排名要小心；
- Critic 打分和人类标注的一致性只是中等（Pearson 0.37–0.47），主观指标只能当诊断参考；
- 消融实验大多只在 GLM-5.1 + Lite 上做，结论是"配置特定"的，不能直接推广到所有模型。

## 5. 论文复现思路

### 5.1 官方资源（已找到并下载）

| 资源 | 位置 |
|---|---|
| 官方评测代码 | <https://github.com/ALEX-nlp/ICAE-EVAL> |
| 本地克隆 | [paper/ICAE-EVAL/](./ICAE-EVAL/)（已 `git clone --depth 1`） |
| arXiv 论文 | <https://arxiv.org/pdf/2607.21217> |
| 仓库内中文说明 | [ICAE-EVAL/task_zh.md](./ICAE-EVAL/task_zh.md)（官方自带，非常实用） |

仓库包含：评测编排器（`harness/`，含 orchestrator、docker 环境、四组评分实现）、User Agent 服务器（`user_agent/`）、一键脚本（`setup.sh` / `run.sh` / `download_scaffold.sh`）、模型配置（`model_list.json`）。

> 注意：公开仓库自带的是 **base 环境 + fuzzy PRD**（对应论文主实验设定）；论文里的 ultimate 镜像、GroundPRD 等部分资源需通过 `setup.sh` 下载，个别数据（如 ultimate 沙箱镜像）是可选项。

### 5.2 复现的最小闭环（推荐路线）

**第 0 步：环境准备**
- 一台装了 Docker 的机器（内存建议 16G+，磁盘 50G+，12 种语言的镜像 + 480 个任务的黄金仓库和测试用例体积不小）
- Python 3.11+（OpenHands 支持需 3.12+）
- 至少一个被测模型的 API（Anthropic 兼容端点即可，`model_list.json` 里配 base_url + token）

**第 1 步：安装并下载数据**
```bash
cd paper/ICAE-EVAL
bash setup.sh          # 建 .venv、装依赖、下载语言镜像 + 黄金仓库 + 权威测试（可断点续传）
# 只装依赖不下载：bash setup.sh --skip-download
```

**第 2 步：配置模型**
- `model_list.json` → 填 `Tested Model`（被测模型）和 `Critic Model`（评审模型）的端点与 token
- `user_agent/user_model.json` → 选 Oracle 模型（默认 DeepSeek-V3.2）
- 若用 Claude Code 跑，按 README 配 `~/.claude/settings.json`（token、base_url、thinking 类型等）

**第 3 步：冒烟测试（1 个任务，验证整条链路通不通）**
```bash
./run.sh               # 默认 Opus-4.8 跑 1 个仓库
./run.sh GLM-5.1      # 换别的模型
```
`run.sh` 会自动：启动本地 Oracle（User Agent）→ 等 3 个端口就绪 → 跑评测 → 收 Oracle。产出在 `results/<append_id>/`。

**第 4 步：跑 Lite 全量（50 个任务，对应论文消融实验的规模）**
```bash
RUN_LIMIT=50 ./run.sh Opus-4.8
```

**第 5 步：复现论文的关键对照实验**

| 论文实验 | 复现方式 |
|---|---|
| 模糊度等级（Fuzzy L1/L2/L3 ≈ normal/medium/easy） | `./run.sh Opus-4.8 --difficulty easy`（normal/medium/easy 对应不同 PRD 目录） |
| 换 Oracle 模型 | `USER_MODEL_NAME=Gemini-3.1-Flash-Lite ./run.sh ...` |
| 换提问预算 | `--query-count 8/16/24`（orchestrator 参数） |
| 换智能体框架 | `--agent-framework openhands`（需 `setup.sh --openhands`） |
| GroundPRD 上限 / RecoveredPRD / 测试脚手架消融 | 见 `harness/config.py` 的 `DETAILED_PRDS_DIR` 覆盖机制与 `task_zh.md`，部分属于高级用法 |

**第 6 步：评分与结果分析**
```bash
python -m harness.orchestrator eval --append-id <id>   # 对已有结果重跑四组评分
```
结果包含：动态测试通过率（Public/Native/Enhanced）、结构相似度、Critic 三项打分、交互质量三项统计。

### 5.3 复现预算与注意事项

- **成本主要在 API 调用**：每个任务一次完整的智能体开发会话（读 PRD、提问 ≤16 次、写代码、自测）+ Critic 评审。论文统计了 token 用量（见 runtime_token_scatter 图），Lite 50 任务 × 多个模型 × 多组消融，费用可观。建议先用 `RUN_LIMIT=1` 冒烟，再 `RUN_LIMIT=10` 小批量估价，最后上 50/480。
- **先跑 Lite**：50 个任务是按代码量最小的挑的，单任务便宜得多，且论文消融都在 Lite 上做的，对照最直接。
- **可复现性**：`results/settings.json` 记录了每次实验（append_id）的配置，同 append_id 可以 resume；评分可以离线重跑（`eval` 子命令），不用重新生成。
- **注意模型名与论文的对应**：论文里的 GPT-5.5、Claude-Opus-4.8、GLM-5.1 等是 2026 年的前沿模型，如果手头只有别的模型，也可以用同样的协议测自己的模型/智能体——这本身就是这个 benchmark 的用法。
- **只想复现"评测"不想跑生成**：如果你能拿到别人跑出的 `results/` 目录，直接 `eval` 子命令就能重算所有指标。

### 5.4 如果想更省事：自建简化版

如果完整复现成本太高（毕竟要 12 种语言的 Docker 镜像和一堆 API），可以做一个"论文思想的迷你复现"来理解机制：

1. 挑 3–5 个带测试的小型开源 Python 仓库；
2. 用一个 LLM 从源码+测试反推一份详细 PRD，并把测试改写成 JSON 黑盒用例；
3. 手工（或用 LLM）把 PRD 删减成模糊版，并把删掉的约束整理成带触发关键词的 Q&A 表；
4. 写一个 ~100 行的 HTTP 服务扮演 User Agent（关键词匹配 Q&A 表 + 兜底回复 + 预算计数）；
5. 把模糊 PRD 交给任意编码智能体（包括 Claude Code CLI），规定它只能通过该服务提问，最后用黑盒用例判卷。

这套流程足以验证论文的核心发现（比如"直接给可执行样例 ≫ 靠问答拿信息"），也是理解这篇论文最好的方式。

| 术语 | 含义 |

| PRD | Product Requirement Document，产品需求文档 |
| GroundPRD | 从原仓库反推出的完整、精确的需求文档（"标准答案版需求"） |
| Fuzzy PRD (L1–L3) | 故意删减/模糊化后的需求，L1 最模糊，L3 最接近完整 |
| User Agent / Oracle | 扮演"用户"的智能体，只能照着预设的问答表回答 |
| Native / Enhanced 用例 | 从原仓库测试改造的用例 / 额外合成的边界鲁棒性用例 |
| Public / Hidden 用例 | 需求文档里公开的示例用例 / 判卷用的隐藏用例 |
| Ultimate Image | 装好依赖但删掉一切答案痕迹的任务 Docker 镜像 |
| Coding Agent | 编码智能体，如 Claude Code、OpenHands |
| Overall Pass Rate | 全部 Native + Enhanced 用例的通过率（论文的主指标） |
| Constraint Coverage | 通过提问成功问回的隐藏约束比例 |
| Fallback Rate | 提问打空（没命中任何预设约束）的比例 |
