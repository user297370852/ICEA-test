# QA 门禁实验报告 —— self-quiz 问答机制对 ICAE-Bench 理解偏差的抑制效果

> 实验时间：2026-10-24 ~ 10-26 · 被测模型 glm-5.3-flash · 框架 claude-code（Claude CLI 2.1.273）·
> Lite 50 任务 · 对照基线：2026-09 完整复现（append_id `5b3b6db753be455aa9bc850574c68cd1`，Overall 47.1%）
> 治疗组：append_id `3992f153f5bf4d0aa80a27105e752e67`
> 交互数据：详见 `run_records_3992f153*/`（settings + summary + 每仓 quiz 判分记录）与 `trajectory/`（未归档）

## 1. 实验定位

《理解偏差案例库与自检问答设计参考》（仓库根目录）从 50 任务失败案例归纳出五类理解偏差
（A 契约未进入心智模型 / B 知道没照做 / C 先验顶替契约 / D 配方错误 / E 未定义分叉），其中
**17/50（34%）仓库在 public 阶段全零且全部是协议/词汇级偏离**。本实验验证的假设是：

> 把隐藏约束卡做成题库、在关键时点强制抽考并当场纠错（"常驻门禁"），能把协议级全零问题基本消除。

门禁机制（v0.3 终版）：

- **G1**：写 dispatcher / 任何 I-O 代码之前，T1（词汇表默写）+ T2（逐字节输出协议）题必须全过（含 FAIL 后的出处复述+复答）；
- **G2**：上下文压缩后，wrong-only 清错（T7 状态重建）；
- **G3**：宣布完成前，T4（条件反面）+ T6（枚举）清错，且**全部 T2 题代码对质**——跑 agent 自己的
  `rcb_tests/test.sh`，stdout 与 golden 做 cmp 级比对；verify 通过后再改代码必须全部重验；
- 判分为确定性脚本（零 LLM 判官开销），题库只由 agent 合法可得的信息构成（public 用例 + oracle 卡片），杜绝评分集泄漏。

## 4. 经典纠错案例（三方证据链：判分记录 × 对话轨迹 × 评测）

### 4.1 @003：模型起手持有的正是 baseline 的错误协议，被门禁在写码前拦下（最典型）

@003 的 baseline 失败是"cov 100% 仍三 suite 全零"——模型流利复述自造的 `results=` 协议。
治疗组轨迹（`trajectory/realcode_003.jsonl`）时间线：

| 时刻 | 事件 |
|---|---|
| 14:08:36 | G1 门禁启动（**尚未写任何 dispatcher 代码**） |
| 14:10:46 | 答 Q003「feature1 stdout」提交 **`result=1`**（自造键名，与 baseline 错误同族）→ byte_equal FAIL |
| 14:10:48 | 复答 **`value=1`** → PASS |
| 14:11:16 | 答 Q005 提交 **`results=1,2,5,6`**（**字面复刻 baseline 的自造聚合协议**）→ FAIL |
| 14:11:23 | 复答 `value=1\nvalue=2\nvalue=5\nvalue=6` → PASS |
| 14:16:15 | **第一份协议相关代码**（`rcb_tests/dispatcher/actions.rb`，含 `value=`）——纠偏完成 5 分钟后才落码 |
| 评测 | 0/26 → **29/32**（hid+enh） |

判分记录（`.qa-bank/realcode@003/records/wrong-record.md`）与评测结果三方印证：模型起手的错误
心智模型与 baseline 同源，门禁在写码前用 golden 出处对齐，代码一次写对。

### 4.2 @026 / @020：同族证据

- @026（baseline 0/79，自造 `{ok:false,error:unknown_action}` 信封）：初始答题不知道 `tag=fn`/`calls=N`
  追踪协议（第 31 字符起不一致）、漏 `initial` 字段 → 纠偏后 78/79。
- @020（baseline 0/143，`error=missing_command`）：初始答案行协议形状错误（`file="foo.txt"="…"` vs
  golden `:foo.txt="…"`）→ 纠偏后 126/143。

### 4.3 @002：代码对质闭环（"知识对了代码错"的修正）

@002 v0.1 回退后，v0.3 重跑的 verify 记录（append_id `df063157`）：

```
15:43:20  Q003 VERIFY-FAIL（feature1_request 输出不完整）
15:43:21  Q004/Q005/Q006 VERIFY-FAIL
15:43:37  Q003/Q004/Q005/Q006 VERIFY-PASS（16 秒内修复全部字节差异）
评测     53/54 —— 与 baseline 持平，成本 $1.60 < baseline $2.00
```

### 4.4 @043：沉默契约（空期望也是契约）

@043 的 public 用例全部期望**空输出**（`{"points": []}` → `""`），baseline 恰在空输出用例上多打
`0.000000` 挂掉。v0.2 起空期望作为一等公民出题（答 EMPTY 算对、多打内容判错），最终 146/146 满分。

### 4.5 反面案例：@049 quiz 死循环

@049（全场最贵的哈希配方仓）出现 2407 次判分循环（first_pass 1.6%），agent 在无法取胜的细节上
反复重考（$16.8，但净增仍 +21 cases）。教训：同题连续 FAIL 需要熔断 + "配方型问题答'无配方'
即止损"的引导（参考文档 T5 题型）。

## 5. 残余盲区（5 仓回退，约 -255 cases）

@019（-51）/ @032（-74）/ @042（-79）/ @045（-30）/ @041（-21）呈现同一模式：**quiz 与 verify 全部
通过（如 @019 48 条 verify 记录全 PASS），评测却 no_output**。根因：agent 在 verify 通过后对
`rcb_tests/` 的改动破坏了评测协议兼容性——评测容器注入的是**剥离了 expected_output 的权威用例**
（防作弊设计）且环境全新，agent 的自检 runner 若依赖 `case["expected_output"]`（用来自建对拍）或
未在 test.sh 内完整引导依赖，评测即零输出。**门禁能看到代码字节，看不到评测容器内部**——这是
门禁的边界而非失效；v0.4 方向：`verify` 改为在 fresh 容器（同评测协议）中执行。

## 6. 渠道运营（三层配额实录）

单渠道周配额（ark）+ 兜底渠道（Zcode bigmodel）的 5 小时滚动窗 + 周/月总量，三层限额在跑批中
先后触发；端点池自动轮换（每仓 429 后换渠道重试）+ resume-fill 断点续跑多轮完成全部 50 仓，
未人工干预。细节：SUT/Critic/Oracle 三处均为 ark 主 + Zcode 兜底的双后端池（`harness/creds.py`）。

## 7. 结论

1. **假设成立**：协议级全零（A 类"契约从未进入心智模型"）被门禁基本消除（1.4% → 74.8%），
   整体 Overall +21.2pp；纠错案例（§4）给出"初始错误 → 出处对质 → 代码对齐 → 评测通过"的完整因果链。
2. **成本可控**：+58% 成本换取 +21pp，且协议对齐减少弯路（@003 成本反而低于 baseline：$1.91 vs $2.58）。
3. **机制边界清晰**：门禁覆盖"知识→代码字节"，不覆盖"评测容器环境"；后者需要 fresh-container verify（v0.4）。
4. 方法论完全可复用：题库生成器、门禁注入、确定性判分、A/B 对比均为独立脚本，可对任何同类
   interactive 评测基准复刻。
